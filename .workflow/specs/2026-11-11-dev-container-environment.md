# All the work happens in a dev container, Claude Code included, with the repo in a Docker volume

ADR: `docs/adr/0022-the-work-happens-in-a-dev-container-on-a-volume.md`.

## Why

The tools (node, pnpm, turbo) run in the `dev` compose service, but the editor and Claude Code are on the host, so every command goes through `./dev.sh exec`. `dev.sh` (430 lines) holds about a hundred lines of logic for crossing that boundary, and about as many of profile handling around a list of projects that is empty: signal forwarding through `docker/dev/stop-session.sh` (`dev.sh:195-246`), the check that the checkout is the mounted one (`dev.sh:138-168`), the empty `PROJECTS` (`dev.sh:16`); `docker/README.md:12-36` documents a clone procedure for worktrees because of it. The goal is the owner's, in their words: "poter aggiornare l'intero ambiente indipendentemente dalla mia macchina". No failure is cited: it is the cost of keeping that logic, and of an environment that depends on what the host has.

Moving Claude Code and a push credential into the container also changes what a process in there can reach, which is why the firewall comes with this task and not after it: until today the container held neither a login nor access to the developer's keys.

## What

After the change, on a machine with Windows, a WSL2 distro, Docker Desktop (WSL backend) and VS Code connected to WSL:

- **Creating the environment.** "Dev Containers: Clone Repository in Container Volume" with `git@github.com:enriconardo/enardo-packages.git` (`/tree/<branch>` after it for a branch) builds the stack of `docker/docker-compose.yml` (services `dev` and `playwright`), with the repo at `/workspaces/enardo-packages` in a volume. At creation it enables the firewall, sets `core.hooksPath`, creates a local `main` and runs `pnpm install`, with no action by the human.
- **Commands.** node, pnpm, turbo, git, Claude Code and `pnpm verify` run directly in the container's terminal. There is no `./dev.sh`.
- **git.** Commit and push work from the container with WSL's SSH agent, forwarded by VS Code, holding the developer's own keys: the container has no key of its own. VS Code's forwarding of the host's HTTPS Git credentials is off. `~/.gitconfig` is copied by VS Code.
- **Claude Code.** Installed in the image with the native installer, running as `node`. Login and configuration survive a rebuild, in the named volume at `/home/node/.claude`. The `workflow-overload` marketplace is declared by the repo's `.claude/settings.json`.
- **Firewall.** Outbound traffic is denied except toward the allow list of *Decisions*, the compose network, DNS. It runs at creation before `pnpm install` and at every start. A process running as `node` can only refresh the addresses of the allow list: no run started after the firewall is up opens it, even for a moment.
- **Publishing.** The `publish` skill builds and packs in the container, then shows the human filled-in commands for a WSL terminal: `docker cp` of the tarballs, then `docker run --rm` of `node:24-bookworm` with the tarball folder and `~/.config/pnpm/auth.ini` mounted read-only, running `npx -y pnpm@<version> publish`. Claude cannot launch them.
- **`playwright`** has no way out at runtime: it is only on an internal compose network shared with `dev`.
- **Probes.** `probe_env` is a temporary folder outside the repo, in the container.
- **Line endings.** `.gitattributes` holds `* text=auto eol=lf`.

Out of scope: a base repo shared with other projects; other projects' environments; publishing any package; a CI.

## Decisions

Facts from the probes are marked *(probe)*.

1. **`.devcontainer/devcontainer.json` on the existing compose file**, `dockerComposeFile: "../docker/docker-compose.yml"`, `service: "dev"`, `workspaceFolder: "/workspaces/enardo-packages"`, `remoteUser: "node"`, `updateRemoteUserUID: false` (a volume has no host owner to align with). Extensions: `anthropic.claude-code`, `dbaeumer.vscode-eslint`, `esbenp.prettier-vscode`. Alternatives: a compose file of its own in `.devcontainer/` (two definitions of `playwright`); a single-container devcontainer (loses the service).

2. **The compose file binds nothing of the host.** *(probe)* A compose bind of `..` under Clone in Volume resolves on the Docker host to a path that does not exist there and fails with "Mounts denied" (vscode-remote-release#5388, open). The extension injects the volume at `/workspaces` through its own override file. So both binds of the `dev` service go: `..:/workspaces/enardo-packages` and `${HOME}/.gitconfig`. Unverified: the extension injecting the volume with no mount of the service at `/workspaces` (the issue's maintainer-given workaround binds `../..:/workspaces` so that the injected volume replaces it). The first attempt binds nothing, because `../..` would otherwise expose the owner's whole projects folder if ever used outside a volume; (the alternative of a WSL checkout with *Reopen in Container*, which needs neither the volume nor this, and its cost, are in ADR 0022); **if acceptance A1 fails on this, the fallback is that bind**, on the `dev` service. In that case the bind is replaced by the volume only under Clone in Volume: H2 and A1 change to "the only bind is `../..:/workspaces`, and in the container `/workspaces` is the volume", and the *What* and ADR 0022 point 2 are amended before the merge. Path: `/workspaces/enardo-packages` stays fixed (Dockerfile, compose, store dir); the volume clone takes the default folder name.

3. **`.pnpm-store` stays in the repo folder**, in the volume with `node_modules`, so hard links keep working. `npm_config_store_dir` is unchanged.

4. **Moving to the new environment happens in two stages, because this session is on the host and `verify` needs a working environment.** Stage 1 (host, `./dev.sh exec`) adds everything without breaking `dev.sh`: the two binds move out of `docker/docker-compose.yml` into a temporary `docker/docker-compose.host.yml` that only `dev.sh` adds with a second `-f`. The branch is pushed on the owner's word and the acceptance runs. Stage 2 runs **inside the new container**, resumed from the journal: it deletes `dev.sh`, `stop-session.sh` and the overlay and sets `exec` empty, so that the commit removing the old environment is verified by the new one. Alternatives: a single stage (the last commit could not be verified: `verify` would run on the host, which the rule forbids, or `dev.sh` would be gone); changing the compose file only in stage 2 (the container cannot be created until then).

5. **`dev.sh` is deleted entirely.** `clean` is the only command that keeps a use inside the container: it becomes `scripts/clean.sh`, the same `find`, run with `bash scripts/clean.sh` rather than a pnpm script, because it removes pnpm's own `node_modules`. `up`, `down`, `logs`, `shell` become VS Code's commands (*Reopen in Container*, *Rebuild Container*) and, from WSL, plain `docker logs`/`docker start` on `enardo-packages-playwright-1`; there is no equivalent inside, since the container has no Docker.

6. **The image** (`docker/dev/Dockerfile`, `node:24-bookworm`). *(probe)* The base has git, ssh, curl; it lacks less, iptables, ipset, sudo, dig, jq, aggregate, shellcheck. Added apt packages: `less sudo iptables ipset iproute2 dnsutils aggregate jq`, besides `shellcheck`. `gh` is not added: no credential for it is wanted. Claude Code with the native installer `curl -fsSL https://claude.ai/install.sh | bash` as `node` *(probe: recommended by the docs; the reference dev container still uses npm)*, with `~/.local/bin` on `PATH`; it auto-updates through `downloads.claude.ai`; a rebuild may restore the version of a cached image layer, which then updates itself. `/home/node/.claude` is created and owned by `node` in the image, so the named volume inherits that owner. The `UID`/`GID` remap and its build args go in stage 1, with the rest of the image: on a volume the default uid 1000 of `node` is right, the owner's uid in WSL is 1000 so `dev.sh` keeps working on the branch, and stage 2 then needs no image rebuild. `/etc/profile.d/dev-path.sh` puts `PNPM_HOME` and `~/.local/bin` on `PATH`: Debian's `/etc/profile` resets `PATH` in a login shell (`dev.sh:248-250`), and VS Code's environment probe uses one. GitHub's published SSH host keys go in `/etc/ssh/ssh_known_hosts`, from a file in `docker/dev/`, taken from GitHub's documentation rather than `ssh-keyscan` at build: `~` is not on a volume, and a non-interactive `git push` would fail with "Host key verification failed" after every rebuild. `GIT_PAGER: cat` in compose goes, now that `less` exists and a human uses the terminal: without a TTY git uses no pager anyway.

7. **Claude Code's login in a named volume** of the compose file, `claude-config:/home/node/.claude`, with `CLAUDE_CONFIG_DIR=/home/node/.claude` so that its `.claude.json` is in there too *(probe: as the reference)*. Not bash history, which nobody asked for.

8. **Firewall**: `docker/dev/init-firewall.sh`, copied from Anthropic's `.devcontainer/init-firewall.sh`, installed root-owned in `/usr/local/bin`, runnable by `node` only through one sudoers entry (no other sudo). The `dev` service gets `cap_add: [NET_ADMIN, NET_RAW]`. Differences from the reference, each with its reason:
   - **Port 22 only toward the allow list.** The blanket `OUTPUT --dport 22` and its `INPUT` rule go, since the GitHub ranges cover SSH: otherwise the forwarded agent could be used against any SSH server.
   - **Domains.** Kept: GitHub ranges from `api.github.com/meta` (`web`, `api`, `git`), `registry.npmjs.org` (install, corepack's pnpm), `api.anthropic.com`, `marketplace.visualstudio.com`, `vscode.blob.core.windows.net`, `update.code.visualstudio.com`. Added: `claude.ai`, `claude.com`, `platform.claude.com`, `downloads.claude.ai` *(probe: required for login and updates; the reference's list is outdated for them)* and `fastdl.mongodb.org` (mongod 7.0.24, 82 MB *(probe)*). Removed: `sentry.io`, `statsig.com` (not in the current network requirements). Not added: `storage.googleapis.com` (a shared host, needed only for plugin metadata; added if acceptance shows it is needed), `npm.enriconardo.com` (nothing in the dev container talks to it any more: this repo's internal dependencies are `workspace:^` and the publish is outside).
   - **Compose networks**: the reference's `/24` of the default gateway stays, but with `playwright` on `browsers` it no longer covers it. The bootstrap also resolves `playwright` and allows `OUTPUT` toward its `/24`, before the DROP policies, with no `INPUT` rule: `dev` opens the WebSocket, so established traffic is enough and a compromised browser reaches no port of `dev`; a name that does not resolve fails the bootstrap, closed (`depends_on` starts the service first). The browser pages come back through the same WebSocket (`exposeNetwork: "<loopback>"`, `packages/vitest-config/index.js:50`), so no inbound rule is needed beyond established traffic.
   - **The run's structure replaces the reference's** *(probe, on this machine's kernel 5.15 WSL2, iptables 1.8.9 nf_tables, ipset 7.17)*. As shipped, the script exits 1 at the first domain with a duplicate A record (`ipset add`: "it's already added"), before the DROP policies, so it leaves the network open: every `ipset add` takes `-exist`. Run a second time, it hangs, because `iptables -F` does not reset the DROP policies of the first run and `curl api.github.com/meta` never answers. Setting the policies to `ACCEPT` before the flush would fix the hang, but any process could then run the script through sudo in a loop to open the network. So the script has two modes. It takes a lock (`flock`, on a root-owned file under `/run`, mode 600, which `node` cannot open) so that concurrent runs through sudo wait for each other, and then:
     - **Refresh**, when the `OUTPUT` policy is DROP **and** the set `allowed-domains` exists: touches no iptables rule and no policy. Addresses are fetched and resolved under the rules in force (GitHub is in the set, DNS is open) into a temporary set, then `ipset swap` replaces the allow list atomically. An `EXIT` trap destroys the temporary set, on any way out; a failure leaves the rules and the previous list as they are.
     - **Bootstrap**, in every other case (a fresh network namespace, a previous bootstrap that failed): the only run that needs open egress, since the GitHub ranges cannot be fetched through an empty set. It runs in the lifecycle command, before any user process. It sets the policies to ACCEPT and flushes the `filter` table, fetches and resolves the addresses into the set, adds the rules, sets the DROP policies, then runs the reference's verification (`example.com` refused, GitHub reached). An `EXIT` trap with a success flag set after that verification, not an `ERR` trap (`exit 1` and signals do not fire `ERR`), on any way out but success sets the policies to DROP first, then flushes `filter`, then destroys the set, in that order because `ipset destroy` refuses a set a rule still references, and with each step tolerating failure. So the set never exists with open policies after the script has ended, and the mode cannot be fooled by a killed run.

     The `nat` table is never flushed: in a fresh namespace it holds only Docker's DNS rules, which the reference had to save and restore for that reason. Accepted limit: after a *failed* bootstrap the next run is a bootstrap too, so a `node` process could open the network with it. That state is reported by the failed lifecycle command, and the rule is to fix it before working. Every restart is a bootstrap and needs the network and `api.github.com/meta`, unauthenticated: starting offline or rate-limited fails closed, and the README gives those symptoms and the recovery (re-run the script once the network is back). The same for `playwright` stopped at a restart: `docker start enardo-packages-playwright-1` from WSL, then re-run the script.
   - **IPv6 and DNS**: no `ip6tables` rules, because the network has no IPv6 *(probe: no global address nor route)*; a dual-stack Docker network would leave it open. DNS stays open on UDP 53, as in the reference: a known exfiltration channel accepted here.
   - **The allow list is not a seal.** GitHub and the other allowed hosts can carry data out, and the forwarded agent holds the developer's keys, so while VS Code is attached a process in the container can push to every repo those keys can write to (Decision 10, an accepted risk). A branch ruleset on `main` of this repo, set by the owner on GitHub as a setup step, blocks its deletion and force-pushes.
   - **The Docker gateway** is inside the kept `/24`, so it is reachable from `dev`, as in the reference.
   - **`playwright` is closed, by a change to its service's network.** Its egress was open and it is reachable from `dev`, so a process in `dev` could drive a browser to any URL and carry data out. The owner first asked to keep the service as it is, then chose to close this: the compose file gets a network `browsers` with `internal: true`, the `playwright` service is only on it, `dev` is on `default` and `browsers`. The Dockerfile and the service's image do not change, and its build still has the network. The browsers need no internet at runtime, since the pages come from `dev`'s loopback through the WebSocket (`packages/vitest-config/index.js:50`); not verified until H1 runs.
   - **Why now.** Doing the firewall in a later task would leave Claude's login and the forwarded agent behind an open network in between; the owner's decision was to have it from the start.

   Run twice: `postCreateCommand` runs it **before** `pnpm install`, since `postStartCommand` runs only after `postCreateCommand` and an install would otherwise execute dependencies' scripts with an open network; `postStartCommand` re-runs it at every start, and with `waitFor: "postStartCommand"` the terminal waits for it. The script is idempotent. A failure of the bootstrap leaves DROP, `&&` keeps the install from running after it, VS Code reports the failed lifecycle command, and the rule in the README is to fix it before working. *(probe)* After the script `node` cannot change the rules (`iptables -F`: "you must be root", `CapEff` 0), which holds as long as the sudoers entry names only the script. On this kernel `ipset` and `-m set` work; a compose peer on the gateway's `/24` is reached (the second `/24`, toward `playwright`, is proved by H3), GitHub over HTTPS and SSH, `registry.npmjs.org`, `fastdl.mongodb.org`, `downloads.claude.ai` and `claude.ai` answer; `example.com` is refused at once and SSH to another host fails.

9. **`postCreateCommand`**: `sudo /usr/local/bin/init-firewall.sh && bash .devcontainer/post-create.sh`. The script: `git config core.hooksPath .githooks`; `git rev-parse --verify -q refs/heads/main || git branch main origin/main` (`verify` needs a local `main`; a clone of a branch lacks it, and this needs no network nor agent; a clone without `origin/main` prints a warning and goes on, so that the install still runs); `pnpm install`. Alternatives: `git fetch origin main:main` (needs the agent, which may not be there during the lifecycle).

10. **Credentials: WSL's SSH agent is forwarded, with the developer's own keys**, amended during the acceptance. `docker/README.md`'s rule is rewritten.
   - **The forwarding.** *(read in Dev Containers 0.469.0)* the extension forwards the host's `SSH_AUTH_SOCK` into the container (`dev.containers.forwardWSLServices`, default true, stays on), or, with none, Windows' OpenSSH agent pipe. ssh and git in the container use it as they would in WSL: the container holds no key, and nothing in it is generated or stored. The setup needs an agent in WSL that VS Code's server sees, holding the key the owner pushes with: keychain in `~/.bashrc` and `~/.profile`, `eval "$(keychain --eval --quiet <key>)"`, then a restart of the WSL distro (`wsl --shutdown`), so that the server starts with `SSH_AUTH_SOCK` (a window restart may keep the old server). `wsl --shutdown` stops the whole WSL2 VM, Docker Desktop's engine and every container included, so the README runs it before the first clone, with nothing running. If `ssh-add -l` in the container finds no agent or no key, the README's step is to check `ssh-add -l` in a new WSL terminal, then restart the distro again.
   - **Why, and the accepted risk.** The first version forwarded an agent holding only a deploy key of this repo; the acceptance showed what it costs (a key and an agent kept apart from the account key in WSL, a setup to repeat per project), and the owner chose the ordinary forwarding instead, as on a Linux machine with no container. The risk: while VS Code is attached, every process in the container, dependencies' scripts and Claude Code included, can use the forwarded keys, so an account-wide key lets it push to every repo of the account. It cannot copy a key out of the agent. A key of the container's own, added as a deploy key and with ssh ignoring the forwarded agent (`IdentityAgent none`), would limit that to this repo; it was weighed and left for later, as a backlog candidate of the task, which the owner picks at the close.
   - **Not under `dev.sh`.** The project name is fixed, so `./dev.sh up` would mount the `claude-config` volume in a container with no firewall, where H1 and the acceptance's fix loop run dependencies' code. `docker/docker-compose.host.yml` covers `/home/node/.claude` with a `tmpfs` (compose merges volumes by target), so under `dev.sh` Claude's login is not there.
   - **The ruleset.** The owner adds a branch ruleset on `main` on GitHub (block deletion and force pushes), a setup step of the README. A normal push to `main` stays allowed, since the task's integration merges locally and pushes `main` from the container.
   - **VS Code's Git credentials.** VS Code's other forwarding path is closed: *(probe)* `dev.containers.gitCredentialHelperConfigLocation` defaults to `global`, which installs a helper handing the host's HTTPS Git credentials to the container; the setup sets it to `none` in VS Code's local (Windows) user settings JSON, since it is machine-scoped, and A3 checks that no `credential.helper` points at VS Code's server. WSL's `~/.gitconfig` has `credential.helper = cache`, which is copied and harmless: its cache in the container is empty. `origin` is the SSH URL of the clone.

11. **Publishing** (see ADR). *(probe, pnpm 11.28.6 against a local Verdaccio)* `npx -y pnpm@11.28.6 publish <tarball> --registry <url> --no-git-checks` accepts a tarball, reads `/root/.config/pnpm/auth.ini` mounted read-only, and runs no lifecycle script from a tarball. The skill takes the pnpm version from the root `packageManager` (without its `+sha512…`, a limit it states: `npx` does not check that hash), packs to `/tmp/enardo-pack`, and gives the human `docker cp -a enardo-packages-dev-1:/tmp/enardo-pack/. ~/enardo-publish/`, then the `docker run` for whoami, the dry run and, on approval, the publish, in dependency order. The container runs as `--user node` with the file mounted at `/home/node/.config/pnpm/auth.ini`, so that nothing in WSL ends up owned by root (uid 1000 on both sides). The commands check the file exists first, because a missing bind source would be created as a directory. The first login is the same container with `~/.config/pnpm` (created beforehand) mounted read-write and `pnpm login`. `npm publish` stays forbidden. Limit stated in the skill: the tarball is produced in the dev container, so the human inspects it with `tar tzf`.

12. **`.workflow/config`** (stage 2): `exec =` empty (*the plugin: "empty: run here"*); `probe_env = env -C "$(mktemp -d)"`, a temporary folder outside the repo, subject to the allow list; the value is read by the prober agent as text. `CLAUDE.md`'s "never `npm i` in the dev container" rule keeps its reason and reads: a probe that needs a package outside the lockfile runs in a temporary folder outside the repo.

13. **Fixed project name stays** (`name: enardo-packages`). *(probe)* Two clones with the same project name collide; one environment at a time is what the owner has. It also means the old stack and the new one are the same project, so `./dev.sh down` comes before the acceptance.

14. **`.gitattributes`** with `* text=auto eol=lf`. All 348 tracked files are LF today, so the index does not change.

### Risks

- **The volume is the only copy of unpushed work.** `docker/README.md` says what removes it (`docker volume rm`, `docker volume prune --all`, Docker Desktop's *Purge data* and *Clean / Purge*), and the rule: push a branch, work in progress included, before any of these or before removing the container with its volume. The Claude Code volume is separate and only costs a login.
- **RAM of the WSL2 VM.** Docker Desktop shares the VM's limit, set in `%UserProfile%\.wslconfig`. The README gives a `memory=` value and how it was measured: during acceptance, `docker stats --no-stream` from WSL during `verify:all --force`, with in-memory Mongo and the three browsers (today the VM has 11 GiB). The number goes in the README in stage 2. Symptom documented: browser tests missing `connectTimeout`, or the OOM killer.
- **Turbo's cache after an image change.** `docker/dev/Dockerfile`, a newer base image, and the compose file are not in turbo's key, so the rule stays and moves with the section: after *Rebuild Container* that changes the image, run `pnpm verify:all --force`. A new clone starts with an empty cache.
- **The forwarded keys reach every repo they can write to.** While VS Code is attached, any process in the container, dependencies' scripts and Claude Code included, can push with them; it cannot copy a key out. The ruleset protects only `main` of this repo. An accepted risk (Decision 10); the README says it.
- **The firewall's addresses go stale.** A domain is resolved once per run; a CDN changing its address produces connection errors to an allowed host. `sudo /usr/local/bin/init-firewall.sh` re-runs it. README, with the symptom.
- **The firewall's allow list may be incomplete** for VS Code's extension installs and the Claude Code plugin: A2 and A4 check it, and a missing host is added before stage 2.
- **A Dockerfile that changed is not noticed by itself.** `./dev.sh up --build` did it; now the human runs *Rebuild Container* after pulling a change to `docker/`, which rebuilds both services and is the only way to apply a new `playwright` image. The README says so. `docker/README.md:54`'s fallback for an image that cannot be built has no replacement: the first build needs the network.
- **VS Code and the firewall.** A VS Code update needs a new server through the allow list, and closing the window stops the stack (`shutdownAction` default), ending running Claude sessions; the next open is a bootstrap. The README says both.
- **Rollback.** Until stage 2 is merged, `main` still has `dev.sh`. If the acceptance fails, `docker compose -p enardo-packages down` from WSL, since `dev.sh` refuses a stack mounting something else (`dev.sh:152-166`), then `./dev.sh up -d` on the host checkout restores the old stack (same project name).

## Test cases

The change is environment, configuration and docs, so its proof is the acceptance on a real clone, with `pnpm verify` green at every commit. Stage 1's checks run on the host:

- **H1.** `./dev.sh up -d` after stage 1: the stack starts with the overlay; `./dev.sh exec pnpm verify:all --force` is green (`pnpm verify` would select no package: the Dockerfile is not in turbo's key).
- **H2.** `docker compose -f docker/docker-compose.yml config` (no overlay) shows no bind mount on any service, `playwright` only on `browsers`, which is `internal: true`, and `dev` on both networks.
- **H5.** In the stack of H1, from the `playwright` service, a connection to the outside fails, both by name (`https://example.com`) and by a literal public address (a one-line `node` fetch); the same two fetches from `dev` in the same stack, where the firewall is not up under `dev.sh`, succeed; `ws://playwright:3000/` answers from `dev`.
- **H3.** In a throwaway container of the new `dev` image on a user-defined network, with `NET_ADMIN`, `NET_RAW` and a peer named `playwright` on a second, internal network shared with it: `sudo /usr/local/bin/init-firewall.sh` exits 0, twice in a row; `https://example.com` is refused, `https://api.github.com/zen` is reached, `http://playwright:3000/` is reached; as `node`, `iptables -F` fails, and `sudo` of anything but the script is refused. During a re-run, a `node` loop of `curl https://example.com` is refused at every iteration. A bootstrap that fails, once with `api.github.com` unreachable and once with only the resolution of `playwright` coming back empty, exits non-zero with the policies at DROP and no set; the next run after the cause is removed succeeds. A bootstrap that fails after the rules are in (the verification) also ends at DROP with no set and an empty `filter` table. SSH to a host outside the list fails. A refresh that fails exits non-zero, leaves the rules and the previous list in force and no temporary set behind. Two concurrent runs both end with the firewall up.
- **H6.** Under `./dev.sh up -d`, `./dev.sh exec find /home/node/.claude -mindepth 1` prints nothing and `mount` shows it as `tmpfs`.
- **H4.** `shellcheck` covers the new scripts (`pnpm lint:sh`, part of verify); `git ls-files --eol` still shows all LF; `git add --renormalize .` changes nothing.

Acceptance, run by the owner on the pushed branch, after `./dev.sh down`, with the setup of the README done:

- **A1.** Clone Repository in Container Volume from `git@github.com:enriconardo/enardo-packages.git/tree/<branch>`: the container comes up, `origin` is `git@github.com:enriconardo/enardo-packages.git`, named `enardo-packages-dev-1` (`docker ps` from WSL), with both services, the repo at `/workspaces/enardo-packages` on a volume, `pnpm install` done, `git config core.hooksPath` is `.githooks`, a local `main` exists, no host path is mounted (`mount | grep workspaces` is the volume), the tree is owned by `node` and `git status` works without a `safe.directory` error.
- **A2.** The VS Code extensions listed are installed.
