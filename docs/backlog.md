# Backlog

Work that is queued or proposed but not started. Each item becomes a branch, opened with `/overload`.

- **Adding items.** An item enters *To evaluate* when a review or an analysis finds it. It moves to *Queued* when the user approves it.
- **Removing items.** A branch removes its own item, in a commit of its own before the merge, so the item leaves this file with the merge: the spec and the git history keep the record. A dropped item moves to *Dropped*, with the reason.
- **Format.** Every item takes a few lines, and says what, why, and where it comes from; the probes of its work go in its branch's spec. It names its source in full, never as "the same review": the item that named the review may leave the file first. Items refer to each other by branch name, not by number: numbers change as the queue moves.

## Queued

In the order approved.

- **`feature/entities/lean-aggregate-core`: a lean core for `@enardo/entities` 3.0.0.** Tier L, a new major.
  - The core stays: `Entity` compared by identity, the aggregate that collects its own events and hands them over with `pullEvents`, the state as an immutable snapshot, a protected `setAttribute`.
  - `Entity<TId>` takes the id's type, so ids can differ by aggregate (`Id<"User">`, or the subclass's own); one `EntityId` for every aggregate lets a `UserId` pass where a `ProductId` is expected.
  - `AggregateRoot<TId, TEvent>` takes the event's type, with `raise(event)` protected and `pullEvents(): TEvent[]`. The dependency on `@enardo/events` goes: the app picks `TEvent` (a union of the aggregate's events), extending `Event` if it publishes them.
  - Out of the base class: the generic `<model>.created/updated/deleted` events and their merge (change notifications, not domain events: see `feature/uow-repository/commit-change-set`), `createdAt`/`updatedAt` bumped on every mutation, `markForRemoval` (a lifecycle the change tracker already holds; a domain with a real end names it, `archive()`), the public `addEvent` and `create*Event`.
  - Fixed on the way, found by a probe on 2.0.0 (2026-11-10): `create({ id })` compiles with required attributes missing (the `this: { prototype }` typing and its cast); `_attributes`, `_events` and `_isMarkedForRemoval` are public and writable, so outside code rewrites a removed aggregate and queues a forged event; `deepFreeze` leaves Map, Set and Date mutable while its test checks only `Object.isFrozen`; `onBeforeAttributeMutation` runs on a no-op, against its JSDoc. Immutability rests on `readonly` types and private state, rather than a promise the runtime breaks.
  - `cambusa`'s six packages are on `^1.1.0` and migrate when they take the major.
  - From the analysis of `@enardo/entities` on `docs/repo/entities-events-backlog` (2026-11-10).
- **`feature/uow-repository/commit-change-set`: the change set of a commit, for change notifications.** Tier L.
  - The change tracker already knows which entities are new, changed and removed, and which fields change (the diff of the mapper's output, ADR 0019): at commit it exposes them, with no dependency on `@enardo/events`. The app, or an outbox, turns them into events.
  - It replaces the `<model>.created/updated/deleted` events of `@enardo/entities`, with data the store confirms and one notification per entity, so nothing is left to merge.
  - From the analysis of `@enardo/entities` on `docs/repo/entities-events-backlog` (2026-11-10).
- **`feature/events/drop-mergeable-event`: `MergeableEvent` and `isMergeableEvent` leave `@enardo/events`.** Tier L, a new major. After `feature/entities/lean-aggregate-core`.
  - Their only use is the merge of the `updated` events of `@enardo/entities`, which leaves with that branch: domain events are facts, and are never merged. `Event`, `EventBus`, `EventHandler`, `EventContext` and `SyncEventBus` stay, as the contract of dispatch.
  - From the analysis of `@enardo/entities` on `docs/repo/entities-events-backlog` (2026-11-10).
- **Three doubts on the dispatch of `@enardo/events`**, to analyze before a change. Tier to decide with the analysis.
  - `subscribe(eventName, handler)` does not tie the name to the handler's event type: a handler of one event subscribes to another and compiles.
  - `EventContext.session?: unknown` carries the transaction into the handlers, and so decides unsaid whether they run inside it or after the commit: an outbox has to decide it.
  - `SyncEventBus` is async and sequential, and stops at the first handler that throws, without saying the others did not run.
  - From the analysis of `@enardo/entities` on `docs/repo/entities-events-backlog` (2026-11-10).

## To evaluate

- **pnpm 12** (12.15.0 on 2026-10-23), deferred while 11 gets fixes: nothing here needs it yet. Tier L. Found in a throwaway clone:
  - it ignores `npm_config_store_dir`, so the store moves into `node_modules/` and the first install downloads everything again: `pnpm_config_store_dir`, which 11 reads too, goes in `docker/docker-compose.yml` and `docker/README.md`, with the dev container recreated;
  - the lockfile gains a leading `packageManagerDependencies` document (+158 lines), and `audit --json` counts its entries;
  - every fresh container downloads a 58 MB native binary, and each install runs a supply-chain check over the network (about 5 s);
  - `verify:all` and `pack` manifests match 11; turbo's key does not hold the pnpm version, so the checks run with `--force`.
  - From the intake of `chore/repo/upgrade-pnpm-11-28` and its `critic` run (2026-10-23).
- **No test runs a browser's own `fetch`.**
  - Every test of `@enardo/http-client` that runs in a browser stubs `fetchImpl`. What only a real `fetch` does in a browser stays untested there: CORS, a stream body and `duplex`, redirects, its rejections. Node's `fetch` is tested against local servers.
  - A page would need a server it can reach: Vitest's own, or one in the dev container exposed through Playwright's `exposeNetwork`.
  - From the spec of `chore/repo/browser-tests` (2026-10-07).
- **`EPROXY` of `@enardo/email-nodemailer` comes out `retryable: false`, for an outage too.**
  - A proxy that answers `503`, or closes before the tunnel, gives `EPROXY`; so do a `407` and a missing socks module. The status is only in the `message`, so the code cannot tell them apart.
  - `retryable` says that the same send may succeed later, and the rule already counts a wrong host as retryable, since a caller bounds its retries while a transient failure taken for a permanent one loses the message. The same reasoning puts `EPROXY` in `CONNECTION_FAILURES`. Tier M: documented behavior changes.
  - To take up when a project configures a proxy: `cambusa`, the only consumer, does not (2026-11-09).
  - From the second review of `feature/email/send-errors` (2026-10-20), and the analysis of this item on nodemailer 10.1.0 and 10.4.0, source read, not run (2026-11-09).

## Dropped

- **`INVALID_ENTITY_ID` of `@enardo/entities`, against ADR 0012 point 6** (2026-11-05). It stays a `BaseError`: `cambusa` calls `EntityId.create` on the parameters of a request, so the value comes from outside, and an app can map the `code` as it does its other value objects' (ADR 0018). From the spec of `fix/email-nodemailer/native-misuse-errors` (2026-11-05).
- **Does `isBaseErrorLike` still earn its place, when apps compare `code` with an allowlist (ADR 0012 point 7)?** (2026-11-05) Yes. The brand is the only namespace of the codes, which ADR 0012 point 4 leaves unprefixed: without it, a foreign error with a generic `code` (`NOT_FOUND`, `CONFLICT`) that an allowlist holds passes as an error of the ecosystem, and `cambusa`'s handler would answer it without logging. The guard is a few lines, and the brand stays on `BaseError` while published `cqrs` and `uow-repository` check it, so removing the export saves little and costs a major of `@enardo/errors`. `cambusa` is no evidence either way: it resolves `@enardo/errors@1.0.0`, which has no brand. The practice agrees: Node documents `code` as the stable identifier, Fastify prefixes it, axios and LiveKit brand. From the discussion at checkpoint 1 of `fix/uow-repository/native-misuse-errors` (2026-11-02).

- **`fix/errors/proto-key-in-serialize`** (2026-10-02). `serializeError` drops an own `__proto__` field of an error. Such a field can only be created on purpose, with `Object.defineProperty` or a computed class field. Untrusted input belongs in `details`, which already keeps the key. Copying parsed input onto an error with `Object.assign` replaces its prototype instead, and no code in the monorepo does that.
- **A sync `Iterable<Uint8Array>` body is sent as a string on Node** (2026-10-22). `HttpBody` accepts it with the Node types, and Node's `fetch` sends it as `[object Generator]` or `104,105`. `@enardo/http-client`'s README already documents it. Leaving it out of `HttpBody` is a new major for a case no consumer has; rejecting it at runtime needs a list of the iterable bodies `fetch` takes (`URLSearchParams`, `FormData`). From the spec of `fix/http/stream-body-duplex`.
- **Split `@enardo/logger`** (2026-10-22) into a contract and a winston adapter. Winston is a detail the app never picks: it chooses a transport, not an engine, so the package stays opaque (root `CLAUDE.md`, *Architecture conventions*). The local copies of `Logger` in `cqrs` and `http-client` are on purpose: each holds the part it uses, and `Logger` is assignable to all of them. Decided after the architectural review of `@enardo/logger` (2026-10-22).
- **A check of the codes' uniqueness in `pnpm verify`** (2026-10-23). ADR 0012 already records it as an alternative set aside until a first collision, with the reasons: it covers this repo only, misses the value passed to `super`, and adds time to every verify and a script to maintain. The likelier collision, between a project's code and a package's, is outside its reach. From the spec of `feature/errors/brand-recognition`.
- **A manifest and README check in `pnpm verify`** (2026-10-26). A script checking each library package's manifest and README against the rules of the root `CLAUDE.md` (`files`, `sideEffects`, the standard scripts, `publishConfig.registry`, `catalog:`, the packages a README names, the contract as a peer and a dev dependency). Excess zeal: it adds a script to maintain for rules that a review already checks. From the spec of `chore/repo/lean-workflow` (2026-10-16).
- **An error of another realm is not recognized by the logger** (2026-10-26). An error from `vm` or a Jest environment fails `instanceof Error`, so `toLoggable` and `serializeError` treat it as a plain object; `Error.isError` would recognize it. No code in the repo, nor an app's log path, meets one; `Error.isError` is missing from Node 22 and from the `ES2022` lib of the presets, and both serializers would need the change. From the review of `fix/logger/serialize-nested-errors`, and the spec of `fix/repo/aggregate-error-errors`.
- **A path can climb above the path of `@enardo/http-client`'s `baseUrl`** (2026-11-02). The parser resolves dot segments, so `../admin` against `https://api.example.com/v2/` gives `https://api.example.com/admin` (probed on 2026-11-02). The client stays as it is, and its README says so. The option in the item, rejecting a URL that ends above the base's path, left `..` and `../admin` under a base with a path and did nothing for a base without one; rejecting every dot segment of a string resource is a new major, and the common practice is the caller's: axios, ky and openapi-fetch join the path and check nothing, and OWASP puts the check in the caller's input validation. Only a client that knows which part is a parameter can check it, as the `path` tag of Anthropic's TypeScript SDK does. If a project needs it, an opt-in helper of that kind is a minor. From the spec of `fix/http-client/base-url` (2026-10-06).
- **`no-restricted-exports` on `src/` in the presets** (2026-11-02). A lint rule to keep default exports out, once `refactor/database-mongo/named-export` removed the last one. No default export was added since the import of the packages (`git log -G`), and no importer in this repo's history used another name; what it would prevent is one rename, caught at review. Added later, it costs a major of `@enardo/eslint-config`. From the spec of `chore/http/package-hygiene`, and the `critic`'s run at the intake of that branch.
- **`BcryptPasswordHasher` reads only the first 72 bytes of a password** (2026-11-03). bcrypt ignored what follows them, and encoded each lone surrogate as U+FFFD. The user chose to change the algorithm rather than patch the adapter: `@enardo/password-hasher` 3.0.0 hashes with Argon2id on `node:crypto`, every byte counts, it refuses a lone surrogate, and `@enardo/password-hasher-bcrypt` leaves the repo (ADR 0016). From the spec of `feature/password-hasher/argon2id-single-package`.
- **`@typescript-eslint/naming-convention` in the presets, against the `I` prefix** (2026-11-05). A lint rule to keep the prefix out of exported types, queued with their rename. No type took the prefix since the import of the packages, `cambusa` declares none, and once the rename leaves none to copy, review is enough, the reasoning that dropped `no-restricted-exports`. The rule would bind the projects, its checks would be manual, and it would miss `IHTTPClient` and `export type { Plain as IFoo }`. Added later, it costs a major of `@enardo/eslint-config` once 2.0.0 is out. From `docs/specs/2026-11-05-drop-i-prefix.md`, decision 3, and ADR 0017.
- **`serializeError` of `@enardo/errors` never calls a nested cause's `toJSON()`** (2026-11-09). No error class in the monorepo overrides `toJSON()`, and an override would stay no way to keep a value out of the logs: `util.inspect` never calls it, so `NetworkError` of `@enardo/http-client` would go on reducing its `cause` in the constructor. The READMEs of `@enardo/errors` and `@enardo/logger` state the limit. To reopen at the first error class that needs an override. What passed the tests of every dependent on a prototype: the ancestors in a module-level stack, since `toJSON()` takes no arguments and an override calling `super.toJSON()` would not forward any; `toJSON()` called on every `Error` cause; one that throws gives `"[Unserializable]"`, since walking the fields would expose what it hides. Each `BaseError` of the chain is then serialized by its own copy of the package. From the spec of `fix/http-client/redact-cause` (2026-10-06), and the `critic`'s run on a spec of the fix (2026-11-09).
- **An outage of the OAuth2 token endpoint comes out `retryable: false` in `@enardo/email-nodemailer`** (2026-11-09). It stays so. A `503` with an HTML body gives `EAUTH`, `AUTH XOAUTH2`, with no `originalCode`, and nodemailer hands over only the body, so the HTTP status never reaches the error. `EOAUTH2` is nearly always permanent (`invalid_grant`, `invalid_client`): retrying it would resend on revoked credentials, to cover `temporarily_unavailable`, which RFC 6749 defines for the authorization endpoint and not in the token endpoint's list (section 5.2, read from an extract), and which only reading the `message` could detect. No project uses OAuth2: `cambusa` does not. From the second review of `feature/email/send-errors` (2026-10-20).
