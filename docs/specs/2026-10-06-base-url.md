# `@enardo/http-client`: `baseUrl` loses its path, and a URL with credentials loses its reason

## Report

The first queued item of the backlog, a prerequisite for server use. From the architectural review of `@enardo/http` (2026-09-25); the credentials part from the spec of `fix/http-client/redact-cause` (2026-10-06).

Probed on `master` (`869e893`), on Node 24.21.0, through the built `dist/` (`turbo run build --filter=@enardo/http-client... --force`, which rebuilds `@enardo/errors` and `@enardo/http-status` too), with a stub `fetchImpl` that records the URL it gets:

| `baseUrl` | resource | URL sent |
| --- | --- | --- |
| `https://api.example.com/v2/` | `/users` | `https://api.example.com/users` |
| `https://api.example.com/v2/` | `users` | `https://api.example.com/v2/users` |
| `https://api.example.com/v2` | `users` | `https://api.example.com/users` |
| `https://api.example.com/v2/` | `//evil.example.com/x` | `https://evil.example.com/x` |
| `https://api.example.com/v2/` | `https://other.example.com/x` | `https://other.example.com/x` |
| `https://api.example.com/v2/` | `users:1` | `users:1` |
| `https://api.example.com/v2/?key=k` | `users` | `https://api.example.com/v2/users`: the query is dropped |
| `ftp://api.example.com/v2/` | `users` | `ftp://api.example.com/v2/users` |
| `https://alice:hunter2@api.example.com/v2/?k=q-secret` | `/users` | `https://alice:hunter2@api.example.com/users` |

- **The constructor checks nothing.** A relative `baseUrl` (`/api/`) fails at each request, with the `TypeError` of `new URL()`, whose own fields `input` and `base` hold the resource and the `baseUrl`.
- **The constructor keeps the `baseUrl` it is given.** A `URL` changed after the constructor (`pathname = "/v3/"`) changes the next requests.
- **`@cambusa/web` loses a base path too.** It passes `${VITE_API_BASE_URL}/` and paths that start with `/`. The default, `http://localhost:3010`, has no path. With `http://localhost:3010/api`, `/auth/authenticate` goes to `http://localhost:3010/auth/authenticate`.
- **A URL with credentials reaches `fetchImpl`.** Node's `fetch` rejects it with `Request cannot be constructed from a URL that includes credentials: <the URL>`. Since `fix/http-client/redact-cause`, the `NetworkError` keeps `{ name: "TypeError" }` of it, so the reason is lost.

## Root cause

`makeUrl` resolves the resource with `new URL(resource, baseUrl)`: a relative reference, by the rules of the URL standard. A path that starts with `/` replaces the base's path; one without replaces its last segment; `//` replaces its host; a string with a scheme replaces it all. The constructor stores `options.baseUrl` as it is: it neither checks nor copies it.

## Fix

### The constructor checks `baseUrl`

`baseUrl` is parsed once, with `new URL(baseUrl)`. `undefined` means no base, as today. Any other value is checked, in this order:

| `baseUrl` | Thrown |
| --- | --- |
| not an absolute URL: `""`, `/api`, `api.example.com` | the `TypeError` of `new URL()` (`code` `ERR_INVALID_URL` on Node) |
| a scheme other than `http:` and `https:`: `ftp://…`, `file:///…`, `localhost:3010` (parsed with the scheme `localhost:`) | `TypeError: Expected an http or https baseUrl` |
| credentials: `https://alice:hunter2@…`, `https://alice@…`, `https://:hunter2@…` | `TypeError: Expected a baseUrl without credentials` |
| a query string or a fragment: `…/v2?key=k`, `…/v2#f` | `TypeError: Expected a baseUrl without a query string or a fragment` |

- **The three messages hold no part of the URL.** The `TypeError` of `new URL()` holds the `baseUrl` in its own field `input`, as it does today for a request's URL.
- **A `?` or a `#` with nothing after it passes.** `URL` reports both as empty (`search` and `hash` are `""`, probed), and the client drops them.
- **An empty `baseUrl` now throws.** Today `""` means no base (`this.baseUrl ? …`). An env var left empty is a configuration error, and the client now says so when it is built.
- **The client keeps its own copy.** Changing a `URL` given as `baseUrl` after the constructor changes nothing.
- **Why only http and https:** the client makes HTTP requests, and the join below starts from the base's `origin`. For `file:`, `data:` and the schemes `URL` does not know (`localhost:3010`), `origin` is `"null"` (probed).

### With a `baseUrl`, a string resource is a path under it

The URL is `<origin of baseUrl><path of baseUrl>/<resource>`, parsed with `new URL()`. One trailing `/` of the base's path and one leading `/` of the resource are dropped first, so both are optional:

| `baseUrl` | resource | URL sent |
| --- | --- | --- |
| `https://api.example.com` or `https://api.example.com/` | `/users` or `users` | `https://api.example.com/users` |
| `https://api.example.com/v2` or `https://api.example.com/v2/` | `/users` or `users` | `https://api.example.com/v2/users` |
| `http://localhost:3010/api` | `/auth/register` | `http://localhost:3010/api/auth/register` |
| `https://api.example.com/v2/` | `""` or `/` | `https://api.example.com/v2/` |
| `https://api.example.com/v2/` | `/users?page=2#top`, with `query: { tag: "a" }` | `https://api.example.com/v2/users?page=2&tag=a#top` |
| `https://api.example.com/v2/` | `//evil.example.com/x` | `https://api.example.com/v2//evil.example.com/x` |
| `https://api.example.com/v2/` | `https://other.example.com/x` | `https://api.example.com/v2/https://other.example.com/x` |
| `https://api.example.com/v2/` | `\\evil.example.com/x` (two backslashes) | `https://api.example.com/v2///evil.example.com/x` |
| `https://api.example.com/v2/` | `users:1` | `https://api.example.com/v2/users:1` |
| `https://api.example.com/v2/` | `alice:hunter2@evil.example.com/x` | `https://api.example.com/v2/alice:hunter2@evil.example.com/x` |
| `https://api.example.com/v2/` | `../admin` or `%2e%2e/admin` | `https://api.example.com/admin` |

Probed with the rule as a stand-in function, in JavaScript, outside the package. The `query` row was probed on `master`, where `/users?page=2#top` against `https://api.example.com/` gives `https://api.example.com/users?page=2&tag=a#top`: the client appends `query` after the path's own query string, and keeps the fragment.

- **A string never leaves the origin of `baseUrl`.** After `<origin>/`, the parser reads a path: nothing in the resource can change the scheme, the host or the port. **Amended after review**: this is read from the URL standard. The review supported it by running 160,000 random strings of `/`, `\`, `:`, `@`, `?`, `#`, `.`, `%`, brackets, tabs, newlines, NUL and fullwidth slashes against four bases: none changed the origin, carried credentials or threw.
- **It can leave the path of `baseUrl`.** The parser resolves dot segments (`..`, `.`, and their encoded forms such as `%2e%2e` and `.%2E`), as it does in every URL. An encoded slash (`%2F`) stays as it is. See *Found while exploring*.
- **The join never threw in the probe**, on spaces, `ü`, a NUL, brackets, `%zz`, a lone surrogate, a tab and a newline (the parser drops these two, as in any URL). In the URL standard, a parse fails only before the path (in the scheme, authority, host and port states), and the base's origin settles all of that; this part is read from the standard, not probed.
- **A `URL` resource is used as it is**, with or without a `baseUrl`, as today: it is how a caller reaches another origin. The client copies it, as today, so `query` does not change the caller's object. A resource is a path when `typeof resource === "string"`.
- **Without a `baseUrl`**, a string is an absolute URL, parsed with `new URL(resource)`, as today.

### A URL with credentials is the caller's error

Once the URL is built, and before the headers, a URL whose `username` or `password` is not empty throws `TypeError: Expected a request URL without credentials`. `fetchImpl` is not called, nothing is logged, and the error holds no part of the URL.

- With a `baseUrl`, only a `URL` resource can have credentials: a string stays in the path (the `alice:hunter2@` row above). The check reads the built URL, not the resource.
- **The other way credentials reach Node's `fetch` is a redirect** to a `Location` that has them. Node's `fetch` rejects it with `TypeError: fetch failed`, caused by `Error: cross origin not allowed for request mode "cors"`, to the same origin as to another: no URL in either message, and no other own enumerable field (probed). Its reduced `cause` is `{ name: "TypeError", cause: { name: "Error" } }`.
- **A `fetchImpl` that builds its own URL** can still give Node's `fetch` credentials, and get back the message that holds them. The reduction of `NetworkError` drops it, as today; this branch does not touch it.

### What does not change

- `redactUrl`, the logs, `NetworkError` and `HttpResponseError`.
- The types: `HttpClientOptions["baseUrl"]` stays `string | URL`, and the resource of `request()` and the shortcuts stays `string | URL`.

### Consumers

`@cambusa/web` is the only package that builds an `HttpClient`. With its default `VITE_API_BASE_URL` it builds the same URLs, probed on `master` through `dist/`:

| `VITE_API_BASE_URL` | resource | URL on `master` |
| --- | --- | --- |
| `http://localhost:3010` | `/auth/authenticate` | `http://localhost:3010/auth/authenticate` |
| `http://localhost:3010` | `/groups`, `query: { page: 2, limit: undefined }` | `http://localhost:3010/groups?page=2` |
| `http://localhost:3010` | `/groups/g%201/list-items/i%2F2/acquire` | `http://localhost:3010/groups/g%201/list-items/i%2F2/acquire` |

An invalid or relative `VITE_API_BASE_URL` now throws when `src/lib/api/http.ts` loads, since it builds the `HttpClient` at module level: the app fails to start, where today each request fails with status 0. This follows from the code; it was not probed in a browser.

## Decisions (to confirm at checkpoint 1)

1. **With a `baseUrl`, a string is always a path, even one that looks absolute** (`https://other.example.com/x`, `//evil.example.com/x`). Two alternatives:
   - keep today's rule for an absolute string: a path built from untrusted input could then change the origin;
   - reject it: a string with a scheme cannot be told from a path such as `users:1`, which the URL standard also reads as absolute.

   To reach another origin, a caller passes a `URL`, or uses a client without `baseUrl`.
2. **A query string or a fragment in `baseUrl` is rejected**, not merged into each request. Today the query is dropped with no error. A fixed parameter goes into each request's `query`, or into a wrapper.
3. **Only `http:` and `https:`**, for the reason given under *The constructor checks `baseUrl`*.
4. **Dot segments are resolved**, as in any URL, and the README says so. Rejecting a path that ends above the base's path would be a check of its own, with its own questions, such as encoded slashes that the upstream may decode. See *Found while exploring*.
5. **The new errors are native `TypeError`s whose messages hold no part of the URL**, like the caller's other errors (`packages/http-client/CLAUDE.md`). The `TypeError` of `new URL()` for a `baseUrl` that does not parse stays as it is, with its `input`, as it does for a request's URL.

## Found while exploring

To add to `docs/backlog.md`, in a commit of its own, if approved:

- **A path can climb above the path of `baseUrl`** with dot segments: `../admin` and `%2e%2e/admin` against `https://api.example.com/v2/` give `https://api.example.com/admin` (probed). A path built from untrusted input, such as `/users/${id}` with `id` set to `..`, reaches another endpoint of the same origin, and `encodeURIComponent` leaves dots as they are. `new URL(resource, baseUrl)` on `master` resolves them the same way. Options: reject a URL whose path ends above the base's path, or leave it to callers. *To evaluate*.

## Out of scope

- **`@cambusa/web`'s slashes**: `config.ts` strips the trailing ones from `VITE_API_BASE_URL`, and `http.ts` adds one back. Harmless now, left as they are.
- **Timeouts and cancellation**: `feature/http-client/timeouts-and-abort`, the next queued item.
- **The scheme of a request's URL without a base** is not checked: `data:` and `blob:` are valid for a browser's `fetch`.
- **Browsers**: not probed; the container has none.

## Test cases

Test-first: a bug fix, on the public API of an `@enardo/*` package. The `test-author` writes them from this spec in one run, in the foreground, in `__tests__/http-client.test.ts`. The tests import from `~/index` only. A stub `fetchImpl` records the URL it gets, compared by `href`.

### The constructor

1. For `""`, `"/api"` and `"api.example.com"`, `new HttpClient({ baseUrl })` throws a `TypeError` whose `code` is `ERR_INVALID_URL`.
2. For `"ftp://api.example.com/"`, `"file:///srv/api/"` and `"localhost:3010"`, it throws a `TypeError` with the message `Expected an http or https baseUrl`.
3. For `"https://alice:hunter2@api.example.com/v2/"`, `"https://alice@api.example.com/v2/"`, `"https://:hunter2@api.example.com/v2/"`, and the first one as a `URL`, it throws a `TypeError` with the message `Expected a baseUrl without credentials`. `util.inspect(error)` holds neither `alice` nor `hunter2`.
4. For `"https://api.example.com/v2?key=q-secret"` and `"https://api.example.com/v2#frag-secret"`, it throws a `TypeError` with the message `Expected a baseUrl without a query string or a fragment`. `util.inspect(error)` holds neither `q-secret` nor `frag-secret`.
5. A `URL` given as `baseUrl` (`https://api.example.com/v2/`) and changed after the constructor (`pathname = "/v3/"`) does not change the requests: `/users` goes to `https://api.example.com/v2/users`.

The existing cases *should accept a baseUrl* and *should throw Error when fetch is not available* stay.

### The URL of a request

6. Each row of the join table under *Fix* is a case, checked against the URL `fetchImpl` gets. A row with two bases or two resources gives a case for each combination. The `query` row passes `query: { tag: "a" }`.
7. A `URL` resource with a `baseUrl` (`new URL("https://other.example.com/x")`, against `https://api.example.com/v2/`) goes to `https://other.example.com/x`. With `query: { a: 1 }`, `fetchImpl` gets `https://other.example.com/x?a=1` in another object than the caller's (`not.toBe`), and the caller's `href` is unchanged.
8. Without a `baseUrl`, the string `https://api.example.com/users` goes as it is.

### A URL with credentials

9. A request rejects with a `TypeError` with the message `Expected a request URL without credentials`, does not call `fetchImpl`, and logs nothing; `util.inspect(error)` holds none of `alice`, `hunter2`, `q-secret`. One case for each URL:
   - the string `https://alice:hunter2@api.example.com/v1/users?token=q-secret`, without a `baseUrl`;
   - the same as a `URL`, with the `baseUrl` `https://api.example.com/v2/`;
   - `https://alice@api.example.com/?token=q-secret` and `https://:hunter2@api.example.com/?token=q-secret`, without a `baseUrl`.
10. The error is not a `NetworkError`.
